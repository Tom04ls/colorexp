# 元ZIPの分析と移行方針

## 実際に確認した範囲

exp1.zip / exp2.zip のhtdocsを展開し、16ファイルずつ照合しました。原本は作業用領域に隔離し、認証情報や旧保存先を納品ソースへコピーしていません。ファイル単位のハッシュと同一／相違は `source-audit.json` に記録しました。

- `script.js` と `styles.css` は2プロジェクト間で完全一致。
- `index.php`、`Page2.php`、`welcome.php`、`thankyou.php`、画像類等も一致。
- DB接続ファイル、保存処理、開始画面、味覚による見出し変換等に差分。
- SQLデータベースのダンプ、元Google Apps Script本体、HSL Analyzer本体は添付なし。
- 味覚名はDBから取得していました。新プロジェクトでは両RDページの条件分岐で実際に参照されている `Sweetness.` / `Sourness.` / `Saltiness.` / `Bitterness.` / `Umaminess.` / `Spiciness.` と、その分岐に対応する `Sweetest` / `Sourest` / `Saltiest` / `Most bitter` / `Most umami` / `Spiciest` を採用しています。DBに別の値が入っていたかどうかはダンプがないため照合できません。

## 150色

元のgenerateColors()は、Hueを0から330まで30刻みで12段階、その各Hueについて次の12組を順番に連結しています。

```text
(S,L):
(25,75) (50,75) (75,75) (100,75)
(25,50) (50,50) (75,50) (100,50)
(100,25) (75,25) (50,25) (25,25)
```

最後に `(H,S,L)=(0,0,100),(0,0,80),(0,0,60),(0,0,40),(0,0,20),(0,0,0)`。

新しいColorIDはこの配列を1始まりにしたものです。色そのものの定義と正規配列順を維持しています。RDでは、このColorID配列をコピーしてシャッフルします。色ID自体をシャッフル後に付け直すことはしません。

### 元コード内にある異なる色番号

`script.js` 内の `xstack()` は表示RGB文字列から `color1`〜`color150` に変換するハードコード表を持っています。この表はL=25のときSが25→50→75→100の順です。generateColors()では逆順です。

| 新ColorID（元generateColors順） | H | S | L | 旧xstackの色番号 |
|---|---:|---:|---:|---|
| 9 | 0 | 100 | 25 | color12 |
| 10 | 0 | 75 | 25 | color11 |
| 11 | 0 | 50 | 25 | color10 |
| 12 | 0 | 25 | 25 | color9 |

同じ逆転が12Hue分、計48色にあります。それ以外の102色は同番号です。全150色は `palette.csv` を参照。

元RDの有効な保存経路は `checkRatingsAndNavigate2()` → `back-end/save-score.php` で、ランダム化された `questionnaire:colors` 内のh/s/l/ratingを送り、PHPはその配列位置を0始まりのbox_numberとして保存していました。したがってbox_numberを色の恒久IDとみなしてはいけません。

旧xstackは別のローカルPHPへの送信処理も持っていますが、RD画面の送信ボタンから直接使われる保存経路とは別です。Analyzerの仕様が不明な状態で、どちらの色番号規則を採用しているかは断定できません。今回のデータは各回答にHSLを明記し、正規順と旧表順の両方へ変換できるようにしました。RGBへの変換・丸め・文字列比較を色同定には使いません。

## 見た目・英文

ユーザーの追加指示により、新規デザイン、多言語切替、表示サイズの最適化、進捗表示をすべて外しました。

- 共通 `styles.css` は原本をバイト単位でコピー。
- 6参加者ページのstyleブロックは原本と一致。ハッシュは `ui-style-sha256.json`。
- タイル：7.5vh角、上限500px、gap 0.5vw、12行、column方向配置など元CSSのまま。
- 背景色：元の `hsl(h, s%, l%)` で設定。黒以外の枠線 `0.01px solid #000000`、黒の枠線 `0.1px solid #ffffff` も元どおり。
- 点数文字の色条件、1.4vw／太字、フォントKanitの外部CSS指定も維持。
- 英文は開始画面の味覚列挙のみ承認に従って6味覚へ変更。それ以外の固定表示は元のまま。
- PHPの動的値の出力は空のspan等へtextContentで挿入。URL遷移先と保存処理を静的ファイル用に置換。
- `updateColorBoxes()` は元コードで新規span作成直後に古いnull参照へstyleを設定する箇所があったため、新規spanを参照し直す修正のみ実施。見た目の数値は変えていません。
- 新たなズーム・スクロール抑止は別のinteraction-guard.jsとviewport属性で実施。HSL、CSSの寸法や文字を変更する処理はありません。

CSSを保持しているため、元から存在する狭い画面での切れ、端末やブラウザの倍率に依存する配置も基本的にそのままです。新しい自動縮小や再配置は加えていません。OS・ブラウザが強制するズームまではWeb側で完全禁止できません。

## 構成変更

- MySQLの被験者テーブル照会は廃止。入力形式、途中セッションのID／age一致、任意のGoogle側許可ID一覧で管理します。元DBの登録者名簿や年齢照合情報は同梱されていません。
- ST実施を廃止しRDを6味覚実施。
- localStorageで練習・本試行・乱数で決めた配置・確定送信内容を維持。
- 1味覚確定ごとに送信し、保存確認を受け取ってから次へ。
- 失敗時は確定データを保持して再送。Google側の排他ロックとキー／ハッシュによる同一内容照合で重複防止。
- 管理・保存エラー・バックアップは実験画面と別のadmin.html。

新プロジェクト内に旧DBのホスト／ユーザー／パスワードや旧Web App URLは含めていません。
